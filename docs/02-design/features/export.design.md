## 0. Context Anchor

| Key | Value |
|---|---|
| **WHY** | 계정·클라우드보다 먼저 사용자가 자신의 작업을 회수할 수 있는 탈출구를 제공한다. PRD v3 §6-2는 프로젝트 내보내기·가져오기를 1순위로 정하고, §9는 내보내기가 아직 없음을 리스크로 표시한다. |
| **WHO** | 신인 창작자와 공모전 준비생. 자신의 파일로 보관·이동·복구하려는 사람이다. |
| **RISK** | 내보내기가 없거나 가져오기가 기존 작품을 덮어쓰면 사용자 데이터가 잠긴다거나 오히려 소실될 수 있다. 형식 오류를 조용히 삼키면 복구 성공으로 오해한다. |
| **SUCCESS** | 작품 1개와 전체 작품을 JSON으로 다운로드할 수 있고, Markdown 읽기본도 다운로드할 수 있다. 정상 JSON을 다시 가져오면 24블록·인물·로그라인이 동일하며, 충돌 ID는 기존 작품을 바꾸지 않고 새 작품으로 추가된다. 잘못된 JSON·빈 파일·알 수 없는 버전은 이유를 보여주며 거부된다. |
| **SCOPE** | `/library`의 작품별 JSON/Markdown 내보내기, 페이지 상단의 전체 JSON 내보내기·JSON 가져오기, 버전 봉투 v1, 파일명 생성, 순수 변환·검증 함수와 테스트. |

## 1. 기능 요구사항

**갭 분석의 대조 단위다.** 한 줄에 하나씩, 검증 가능하게 쓴다.

| ID | 요구사항 | PRD 근거 | 우선순위 |
|---|---|---|---|
| R1 | 작품 1개를 내보내면 `{ format: "modu-story-work", version: 1, exportedAt: <epoch ms>, work: Work }` 형태의 JSON 파일을 생성해야 한다. | §6-2 1번 “JSON + Markdown 다운로드” (버전 봉투는 설계 결정) | P0 |
| R2 | 전체 내보내기를 실행하면 단일 `work` 대신 `works: Work[]`를 가진 동일한 버전 봉투의 JSON 파일을 생성해야 한다. | §6-2 1번, §9 “내 서재 — 다중 작품 저장” (전체 봉투는 설계 결정) | P0 |
| R3 | 가져오기는 `format`이 `modu-story-work`이고 `version`이 지원되는 `1`이며, 단일 `work` 또는 전체 `works`가 유효한 Work 데이터일 때만 성공해야 한다. | §6-2 1번 “JSON 복구” (봉투 검증은 설계 결정) | P0 |
| R4 | JSON이 아니거나 빈 파일이거나 형식·필수 필드가 없거나 알 수 없는 `version`이면 가져오기를 거부하고 사용자에게 실패 이유를 보여줘야 한다. | §3-1 P2 정직한 표기, §6-2 1번 (오류 분류는 설계 결정) | P0 |
| R5 | 가져온 Work의 ID가 기존 작품과 겹치면 기존 작품을 덮어쓰지 않고 충돌하지 않는 새 ID를 부여해 추가해야 한다. | §6-2 1번 “데이터 소실 방지” (충돌 정책은 설계 결정) | P0 |
| R6 | Markdown 파일은 제목 → 로그라인 → 프리미스 → 장르/톤/타깃 → 후크 → 인물 표 → 4막별 24블록 → 노트 순서로 구성해야 한다. | §1의 4막·24블록 제품 정의, §6-2 1번 Markdown 다운로드 (구성은 설계 결정) | P1 |
| R7 | Markdown의 24블록은 1막부터 4막까지 묶고, 각 블록에 `index`·`act`·`function`·`beat`를 표시해야 한다. | §1, §3-2 H-F, §6-2 1번 (표시 필드는 설계 결정) | P1 |
| R8 | 파일명은 `{제목}_{YYYYMMDD}.json` 또는 `{제목}_{YYYYMMDD}.md`이며, 제목에서 파일명에 사용할 수 없는 문자를 치환해야 한다. | §6-2 1번 (파일명은 설계 결정) | P1 |
| R9 | 작품별 내보내기 버튼은 `/library`의 각 작품에 있고, 전체 내보내기와 가져오기는 `/library` 상단에 있어야 한다. | §6-2 1번, §9 | P0 |
| R10 | 내보낸 JSON을 다시 가져오면 24블록·인물·로그라인이 원본과 같아야 한다. | §6-2 1번 “JSON 복구”, §1 | P0 |
| R11 | 계정·서버 저장·클라우드 연결 없이 브라우저에서 파일 다운로드와 JSON 가져오기를 완료할 수 있어야 한다. | §6-2 실행 순서: 내보내기를 계정·클라우드보다 먼저 | P0 |

## 2. 비목표 (Non-goals)

- 계정·서버 저장·클라우드 동기화 — 이유: PRD v3 §6-2의 3번·4번 단계이며 이 기능은 탈출구를 먼저 제공한다.
- Markdown 파일을 다시 가져와 구조화된 Work로 복원하는 것 — 이유: PRD v3가 지정한 복구 경로는 JSON이다.
- 기존 작품의 자동 덮어쓰기·병합 — 이유: 가져오기의 목적이 데이터 소실 방지이므로 충돌 시 새 작품 추가를 사용한다.
- 공유 링크, 로그인 기반 다기기 복구, xlsx/docx 변환, 스토리툰 생성 — 이유: 현재 PRD v3 §6-2의 JSON/Markdown 다운로드 범위를 넘는다.
- AI 모델 호출이나 파일 저장소 직접 접근 — 이유: 변환·검증은 순수 함수로 두고 UI가 다운로드·저장을 연결한다.

## 4. API 명세

HTTP API는 해당 없음. `engine/export.ts`는 `window`, `localStorage`, 네트워크, 모델을 직접 사용하지 않는 순수 함수 모듈로 설계한다. `/library`가 결과 문자열을 Blob 다운로드로 연결하고, 가져온 Work를 `WorkStore`에 저장한다.

### `engine/export.ts` 순수 함수 계약

| 항목 | 값 |
|---|---|
| 단일 내보내기 | `exportWork(work, exportedAt): string` → v1 단일 JSON 문자열 |
| 전체 내보내기 | `exportWorks(works, exportedAt): string` → v1 전체 JSON 문자열 |
| Markdown | `workToMarkdown(work): string` → 지정된 순서의 읽기용 Markdown |
| 가져오기 | `parseImport(raw): { works: Work[] }` 또는 사용자에게 보여줄 분류된 오류 |
| 파일명 | `filenameFor(work, format, exportedAt): string` → 제목·날짜·확장자를 정규화한 파일명 |
| 모델 사용 | 사용 안 함 |
| 무키 폴백 | 해당 없음 |
| 호출하는 곳 | `app/library/page.tsx` 신규 호출 |

## 5. 데이터 모델

| 타입 | 정의 위치 | 저장 위치 | 비고 |
|---|---|---|---|
| `Work` | `engine/library.ts` | `WorkStore`가 관리 | JSON의 `work` 또는 `works[]`에 원형 데이터를 담는다. |
| 단일 내보내기 봉투 v1 | `engine/export.ts` 신규 | 다운로드 파일 | `format`, `version`, `exportedAt`, `work`를 필수로 가진다. |
| 전체 내보내기 봉투 v1 | `engine/export.ts` 신규 | 다운로드 파일 | `format`, `version`, `exportedAt`, `works`를 필수로 가지며 `work`는 두지 않는다. |
| Markdown 투영 | `engine/export.ts` 신규 | 다운로드 파일 | 사람이 읽는 형식이며 JSON의 복구 원본이 아니다. |

**JSON 봉투 정본**:

```ts
type SingleEnvelopeV1 = {
  format: "modu-story-work";
  version: 1;
  exportedAt: number; // epoch milliseconds
  work: Work;
};

type CollectionEnvelopeV1 = {
  format: "modu-story-work";
  version: 1;
  exportedAt: number; // epoch milliseconds
  works: Work[];
};
```

`parseImport`는 `format`과 `version`을 먼저 확인한다. `version` 1만 읽고, 형식이 아니거나 모르는 버전이면 조용히 빈 목록을 반환하지 않고 오류 사유를 반환한다. 유효성 검사를 통과한 뒤에도 기존 ID 집합과 가져오기 중 새로 배정한 ID 집합을 함께 비교해 충돌마다 새 ID를 만든다. 기존 Work는 수정하지 않는다.

**저장 경계**: `engine/export.ts`는 저장하지 않는다. UI가 파싱 결과를 `WorkStore.save`로 추가한다. 이 분리로 향후 `localStorage → Dexie → 서버` 전환이 파일 형식 변경과 섞이지 않게 한다. 계정·서버·클라우드 데이터 모델은 이 기능의 범위가 아니다.

## 6. 원칙 준수 (PRD v3 §3)

| 항목 | 이 기능에서의 의미 | 지키는 방법 |
|---|---|---|
| P1 후크는 사람 | 내보내기·가져오기는 사용자의 후크를 보존하는 운반 기능이어야 한다. | JSON에는 `hookNote`를 포함한 원본 Work를 그대로 담고, Markdown에도 후크를 별도 항목으로 표시하며 내용을 생성하지 않는다. |
| P2 정직한 표기 | 파일을 만들었다고 검증·복구가 성공한 것은 아니다. 오류도 결과의 일부다. | 형식·버전·필수 필드 오류를 분류해 사용자에게 보여주고, 내보내기 파일을 AI 검증 완료로 표시하지 않는다. |
| P3 되돌아갈 자유 | 탈출구 자체가 사용자의 어느 단계에서도 파일로 빠져나오는 권리를 보장한다. | JSON을 전체 원본으로 보존하고, 가져오기 충돌 때 덮어쓰지 않으며, Markdown은 읽기본으로 별도 제공한다. |

## 7. 검증 기준

| 검증 | 방법 | 통과 조건 |
|---|---|---|
| 단위 테스트 | `tests/export.test.ts` | 단일·전체 봉투가 정해진 필드를 가지며, `version: 1`을 생성한다. |
| 라운드트립 테스트 | `Work → JSON 내보내기 → JSON 가져오기` | 24블록·인물·로그라인이 원본과 동일하고, 전체 내보내기도 모든 Work를 보존한다. |
| 충돌·오류 테스트 | 기존 ID 충돌, 손상된 JSON, 빈 파일, 형식 불일치, `version` 불일치 | 기존 Work는 변하지 않고 가져온 Work는 새 ID로 추가된다. 모든 오류는 빈 성공 결과가 아니라 사용자 표시용 이유를 낸다. |
| Markdown 테스트 | 4막·24블록이 있는 Work를 변환 | 제목부터 노트까지 순서가 맞고, 각 블록에 `index`·`act`·`function`·`beat`가 표시된다. |
| 파일명 테스트 | 특수문자 제목과 날짜 경계값 | `{제목}_{YYYYMMDD}.json/.md` 형식이며 사용할 수 없는 문자가 치환된다. |
| 타입 | `npx tsc --noEmit` | 에러 0 |
| 빌드 | `npx next build` | 성공 |
| 실사용 | 오케스트레이터가 브라우저에서 직접 | 작품 카드 내보내기, 상단 전체 내보내기, JSON 가져오기, 충돌 추가, 잘못된 파일 오류 표시를 각각 확인한다. |
