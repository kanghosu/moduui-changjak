## 0. Context Anchor

| Key | Value |
|---|---|
| **WHY** | 사용자의 작업이 쌓이고 다시 열려야 재방문 이유가 생긴다. PRD v3 §9는 이를 “내 서재 — 다중 작품 저장”과 “실험 전 스냅샷·버전 복원”으로 정의한다. |
| **WHO** | 신인 창작자와 공모전 준비생. 자신의 이야기 초안과 구조를 다시 열어 이어 쓰는 사람이다. |
| **RISK** | 작품이나 실험 버전을 잃으면 사용자의 소유감과 재방문 기반을 함께 잃는다. 저장된 결과를 AI가 만든 것으로 과장해도 P2를 위반한다. |
| **SUCCESS** | 서로 다른 작품을 2개 이상 저장한 뒤 새 작품을 만들어도 기존 작품이 남고, 각 작품을 다시 작업실에서 열 수 있다. 저장된 스냅샷을 복원하면 해당 시점의 24블록과 사용자 입력이 유지된다. |
| **SCOPE** | 다중 작품 목록, 작품 재방문, 작업실 연결, 스냅샷·버전 복원, 사용자 데이터 보존. 내보내기·가져오기는 별도 `export` 기능에서 다룬다. |

## 1. 기능 요구사항

**갭 분석의 대조 단위다.** 한 줄에 하나씩, 검증 가능하게 쓴다.

| ID | 요구사항 | PRD 근거 | 우선순위 |
|---|---|---|---|
| R1 | 작품을 새로 저장해도 이미 저장된 다른 작품을 목록에서 다시 열 수 있어야 한다. | §9 “작업이 쌓인다” | P0 |
| R2 | 저장된 작품은 사용자가 `/library`에서 식별하고 작업실에서 이어서 편집할 수 있어야 한다. | §9 “내 서재 — 다중 작품 저장”, §6-1 B층 사용자 데이터 | P0 |
| R3 | 실험 전에 만든 스냅샷을 목록에서 선택하면 그 시점의 작품 상태로 복원할 수 있어야 한다. | §9 “잃지 않는다”, §6-1 B층의 스냅샷 | P0 |
| R4 | 단계 사이를 이동하거나 이전 버전을 복원해도 하위 산출물을 삭제하지 않아야 한다. | §3-1 P3 되돌아갈 자유 | P0 |
| R5 | 저장·복원 과정에서 사람이 작성한 후크를 AI가 생성한 내용으로 대체하지 않고 그대로 보존해야 한다. | §3-1 P1 후크는 사람이 채운다 | P1 |
| R6 | 작품의 로그라인·인물·4막·24블록 등 사용자 데이터는 작품을 다시 열 때 동일한 내용으로 제공되어야 한다. | §1 한 줄 정의, §6-1 B층 사용자 데이터 | P0 |

## 2. 비목표 (Non-goals)

- 내보내기·가져오기와 파일 형식 정의 — 이유: PRD v3 §6-2의 1순위인 별도 `export` 기능에서 설계한다.
- 계정·서버 저장·클라우드 동기화 — 이유: PRD v3 §6-2에서 내보내기 이후의 3번·4번 단계다.
- 작품 내용의 생성·추출·로그라인 작성 — 이유: `/create`와 `/studio`의 책임이며, 서재는 저장·재방문 경계에 둔다.
- 저장된 결과를 “검증 완료”로 판정하거나 AI 성능을 새로 보증하는 것 — 이유: PRD v3 §3-1 P2와 §4의 대외 표기 규칙에 어긋난다.

## 3. 화면·컴포넌트

| 화면/컴포넌트 | 파일 | 책임 |
|---|---|---|
| 내 서재 | `app/library/page.tsx` | 여러 작품을 보여주고 작품별로 작업실을 열며, 현재 작품과 스냅샷 복원을 제공한다. |
| 작품 저장소 계약 | `engine/library.ts` | 작품 목록 조회·단건 조회·저장·삭제를 저장소 구현과 분리한다. |
| 작업실 연계 | `/studio` | 서재에서 선택한 작품을 이어서 편집하는 진입점이다. |

**사용자 흐름**: `/library` 진입 → 작품 목록 또는 현재 작품 확인 → 작업실에서 이어쓰기 / 스냅샷 선택 → 복원 후 작업실로 이동

## 4. API 명세

HTTP API는 해당 없음. PRD v3의 현재 범위는 계정·서버 저장 이전이며, 화면은 클라이언트 저장소 계약을 사용한다. 서버 저장 단계로 전환할 때는 §5의 동기 계약을 비동기로 바꾸는 별도 설계가 필요하다.

## 5. 데이터 모델

| 타입 | 정의 위치 | 저장 위치 | 비고 |
|---|---|---|---|
| `Story` | `engine/schema.ts` | 작품 데이터 내부 | 로그라인·프리미스·장르·타깃·톤·인물·24블록·노트를 보존한다. |
| `Work` | `engine/library.ts` | 현재 구현은 `localStorage`의 `mc_works` | 작품 식별자와 `Story`를 묶는 현재 구현 계약이다. PRD가 보장하는 핵심은 작품과 그 하위 사용자 데이터의 보존이다. |
| `CurrentProject` | `engine/library.ts` | 현재 구현은 `localStorage`의 `mc_project` | 작업실의 현재 작품과 스냅샷을 연결하는 현재 구현 계약이다. |
| `WorkStore` | `engine/library.ts` | 저장소 어댑터 | 목록·조회·저장·삭제의 경계를 정의한다. |

**저장 키**: 현재 구현은 다중 작품을 `mc_works`, 작업실의 현재 슬롯을 `mc_project`에 둔다. 저장 매체 자체는 PRD의 최종 목표가 아니다. PRD v3 §6-2는 내보내기를 먼저 넣은 뒤 `localStorage → Dexie(IndexedDB)`로 옮기는 순서를 정한다.

**중요한 인터페이스 제약**: 현재 `WorkStore`는 동기(sync)다. `list(): Work[]`, `get(id): Work | null`, `save(work): void`, `remove(id): void` 형태이므로 서버 저장 시 그대로 어댑터만 교체할 수 없다. PRD v3 §6-4가 지적하듯 Dexie나 서버 저장은 `Promise`를 사용해야 하며, 전환 시 `/library`·`/studio`·`/create`에 로딩·에러·낙관적 업데이트 상태가 추가로 필요하다.

**마이그레이션**: 옛 `mc_project` 단일 슬롯을 어떻게 흡수할지는 PRD v3에 정책으로 정의되어 있지 않다. 현재 코드의 `ensureMigrated()` 동작과 그 판단 근거는 별도 `_unbacked/library.md`에 기록한다.

## 6. 원칙 준수 (PRD v3 §3)

| 항목 | 이 기능에서의 의미 | 지키는 방법 |
|---|---|---|
| P1 후크는 사람 | 서재는 후크를 새로 만들거나 자동 대체하지 않고 사용자가 만든 산출물을 보존한다. | 저장·재방문·복원 시 `hookNote`를 원문 데이터로 유지하고, 후크가 있다는 사실만 상태로 표시한다. |
| P2 정직한 표기 | 서재의 카드나 상태가 저장된 결과의 검증 수준을 부풀리면 안 된다. | 생성 경로와 검증 여부를 혼동하는 카피를 추가하지 않는다. 현재 PRD가 정의하지 않은 “검증 완료” 배지는 요구사항으로 삼지 않는다. |
| P3 되돌아갈 자유 | 다른 단계나 이전 실험으로 돌아가도 작품의 하위 산출물이 남아야 한다. | 작품 재방문과 스냅샷 복원을 분리하고, 복원은 선택한 버전을 현재 작업 대상으로 만드는 방식으로 설계한다. |

## 7. 검증 기준

| 검증 | 방법 | 통과 조건 |
|---|---|---|
| 단위 테스트 | `tests/library.test.ts` | 두 작품을 저장한 뒤 둘 다 남고, 한 작품 재저장이 다른 작품을 덮지 않으며, 손상 데이터가 전체 앱을 중단시키지 않는다. |
| 스냅샷 회귀 | `/studio`에서 스냅샷 생성 후 `/library`에서 복원 | 선택한 시점의 로그라인·24블록·인물·후크가 복원되고 작업실에서 계속할 수 있다. |
| 타입 | `npx tsc --noEmit` | 에러 0 |
| 빌드 | `npx next build` | 성공 |
| 실사용 | 오케스트레이터가 브라우저에서 직접 | 작품 A 저장 → 작품 B 저장 → A를 다시 열어 내용 보존 확인 → 스냅샷 복원 → 작업실에서 이어쓰기 확인 |

## 8. PRD에 근거가 없는 동작 (별도 보고)

> **여기에 쓰지 말고 별도 파일 `docs/02-design/_unbacked/library.md`에 쓴다.**
> 코드에는 있는데 PRD v3에서 근거를 못 찾은 동작을 적는다.
> 이것이 갭의 씨앗이다. 설계문서 본문에 넣으면 갭이 사라져 버린다.
