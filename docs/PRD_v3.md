## 1. 한 줄 정의 (v2 유지)

**떠들면 이야기가 된다** — 신인 창작자가 "내 글"이라는 소유감을 잃지 않으면서, 방법론(욕망의 레시피 4막·24블록)으로 완성 가능한 이야기 구조를 얻는 도구.

## 2. 차별화 — 하나로 좁힌다

리서치 두 갈래가 서로 모르는 채 같은 지점을 가리켰다.

- **학술(B)**: v2의 원칙 6개 중 **"AI가 대신 쓰면 소유감·책임감이 낮아진다"만 반복 재현된 결과**로 지지된다. 사용자 기여·편집·통제가 소유감을 지킨다.
- **시장(C)**: 경쟁 10개 공개 자료에서 **"발화에서 요소를 추출하고 이미 말한 것은 다시 묻지 않는 UX 계약"을 공개한 제품이 없다.**

→ **우리 제품의 축은 "사용자의 말을 존중하는 계약" 하나다.** 24블록도, 10개 질문도, 3안도 이 축을 실현하는 수단이지 그 자체가 자산이 아니다.

> 경쟁 3분류(C): ① 사람이 구조를 채우는 정리 도구(Plottr·Campfire) ② 설정을 주면 장면을 생성하는 AI 작가 도구(Sudowrite·NovelAI·Novelcrafter) ③ 입력을 웹툰으로 바꾸는 제작 도구(툰스툰스·WeToon·GenToon). 우리는 그 사이다.

## 3. 원칙과 가설 — 근거 상태를 표기한다

v2는 6개를 모두 "양보 불가 원칙"이라 적었다. **과장이었다.** 근거 상태로 갈라 적는다.
이 표기 규칙은 v2 원칙 5("정직한 표기")를 우리 문서 자신에게 적용한 것이다.

### 3-1. 원칙 — 근거 있음. 바꾸지 않는다

**P1. 후크는 사람이 채운다.** AI가 전면 대행하면 소유감·책임감이 떨어진다.

> 근거: *The Value, Benefits, and Concerns of Generative AI-Powered Assistance in Writing* (CHI 2024, [10.1145/3613904.3642625](https://doi.org/10.1145/3613904.3642625)) · *Writing with AI Lowers Psychological Ownership, but Longer Prompts Can Help* ([arXiv:2404.03108](https://arxiv.org/abs/2404.03108)) · *The AI Ghostwriter Effect* ([arXiv:2303.03283](https://arxiv.org/abs/2303.03283)) · *How prompting and editing shape psychological ownership* ([10.1016/j.chbah.2026.100381](https://doi.org/10.1016/j.chbah.2026.100381))
>
> **한계**: "반드시 후크 칸이어야 한다"까지는 검증되지 않았다. 검증된 것은 *사용자 기여·편집·통제가 소유감을 지킨다*는 것이다. 어떤 칸을 비워둘지는 우리 설계 판단이다.

**P2. 정직한 표기.** 생성물의 근거가 AI 분석 초안이면 그렇게 쓴다. "검증 완료"로 부풀리지 않는다.

> 근거: 제품 윤리 판단(외부 근거 아님). 이 PRD 자신에게도 적용한다 — 그래서 §3-2가 존재한다.

**P3. 되돌아갈 자유.** 어느 단계로든 이동 가능하고 하위 산출물을 지우지 않는다.

> 근거: 제품 판단. 사용자 통제감을 지킨다는 점에서 P1의 근거와 같은 방향이다.

### 3-2. 가설 — 검증 전까지 원칙이 아니다

| # | 가설 | 근거 상태 | 검증 |
|---|---|---|---|
| **H-A** | 자유 발화 시작이 항목 입력보다 장벽이 낮다 | **직접 비교 연구 없음** | §8 H1 |
| **H-B** | 이미 말한 것을 다시 묻는 것은 치명적이다 | **"치명적"의 근거 없음.** 문맥 추적이 효율을 높인다는 근거만 있음 | §8 H5 |
| **H-C** | 질문 10개 이하면 피로하지 않다 | **10이라는 숫자에 근거 없음** | §8 H2 |
| **H-E** | 로그라인 3안이 1안·5안보다 낫다 | **반박.** 선택 과부하는 맥락 의존이며 3이 최적이란 근거 없음 ([10.1086/651235](https://doi.org/10.1086/651235)) | §8 H3 |
| **H-F** | 4막·24블록이 빈 캔버스보다 초보자에게 낫다 | **부분 지지.** 스캐폴딩 일반론은 지지되나 **24블록 자체는 미검증** | §8 H4 |

**중요 — 코드는 지금 그대로 둔다.** `MAX_QUESTIONS = 10`, 로그라인 3안, 24블록을 바꾸지 않는다. **바꿀 근거도 없기 때문이다.**
바뀌는 것은 **우리가 그것을 뭐라고 부르는가**다. 대외 자료(지원서·소개 페이지·투자 자료)에서 **"검증된 방법론"이라고 쓰지 않는다.**

> **「욕망의 레시피」 24블록 체계를 검증한 동료심사 논문은 찾지 못했다.** 방법론의 권위를 학술로 뒷받침할 수 없다.
> 4막 구조 자체는 영화 코퍼스 기반 기술적 근거가 있다 — Cutting, *Narrative theory and the dynamics of popular movies* ([10.3758/s13423-016-1051-4](https://doi.org/10.3758/s13423-016-1051-4)).

## 4. 지금 실제로 작동하는 것

`/create` 5단계. 무키 상태에서도 전 구간이 돈다. 실행 검증일 2026-08-25.

| 단계 | 화면 | 작동 | 근거 |
|---|---|---|---|
| 1 | 쏟아내기 | 자유 텍스트 + 음성(Web Speech API). 질문 없음 | `app/create`, `components/VoiceInput.tsx` |
| 2 | 뼈대 찾기 | 요소 추출 → 비어 있는 것만 Typeform식 한 화면 한 질문(≤10) + 장면→후보 블록 역산 | `/api/extract`, `/api/scene-blocks` |
| 3 | 이야기 고르기 | 로그라인 3안(정공법/관계/아이러니) + 벤치마크 | `/api/loglines` |
| 4 | 깊게 만들기 | 인물·사건·흐름 심화 + 후크(AI가 채우지 않는 칸) | `/create` |
| 5 | 이야기 지도 | Plottr식 가로 타임라인, 24칸 눈금 등폭 고정 | `/api/generate`, `StoryTimeline` |

**아직 없는 것**: 내보내기, 계정·서버 저장, 스토리툰 생성, 결제, 스트리밍, i18n.

**실키 경로는 미검증이며, 9/5 데모 범위 밖이다** (결정 2026-08-30).
`.env.local`이 없어 지금까지 mock/휴리스틱 경로로만 검증됐다. **데모도 이 경로로 촬영한다.**

> **대외 표기 규칙(P2)**: 데모 영상·지원서·소개 페이지에서 이 산출물을 "AI가 만든 결과"로 제시하지 않는다.
> 현재 보여지는 추출·로그라인은 **규칙 기반 휴리스틱 결과**다. 실제 모델 경로는 아직 검증되지 않았다.
> 부풀리면 P2 위반이고, 심사에서 확인당하면 더 크게 잃는다.

휴리스틱 경로의 실측 상태: 2026-08-25 보강 후 질문 수 8→6개, 장면 배치 근거가 '하나·손에'→'옥상·비리'로 개선됨(§5).

## 5. 최대 리스크 — 추출 품질

"주인공은 평범한 회사원"이라 말했는데 주인공을 다시 묻는 사례가 2026-08-25 실사용에서 나왔다.
H-B가 깨진 것이고, **§2의 차별화 축이 바로 여기서 무너진다.**

v2에서 조치한 것: 주인공·사건·주제·결말·시대 패턴 추가, 장면을 문장 통째로 보존, 벤치마크 매칭 불용어 보강. 질문 8→6개로 감소.

**v3 보강 — 추출 결과의 저장 형식을 바꾼다.**

요소를 `값` 하나로 저장하지 말고 **`값 + 원문 evidence span + 신뢰도 + "모름" 상태`**로 저장한다.
그래야 "이미 말했는가"를 근거로 판정할 수 있고, 반복질문률을 지표로 잴 수 있다.

> 근거: *An Empirical Study on Information Extraction using LLMs* ([arXiv:2305.14450](https://arxiv.org/abs/2305.14450)) · *Are LLMs good at structured outputs?* ([10.1016/j.ipm.2024.103809](https://doi.org/10.1016/j.ipm.2024.103809)) · *SelfCheckGPT* ([arXiv:2303.08896](https://arxiv.org/abs/2303.08896))

측정 지표:

- 요소별 precision / recall / F1, 근거구간 포함률, 누락률, **근거 없는 값 생성률**
- **반복질문률** = (이미 근거가 있는 요소를 다시 물은 질문 수) / (전체 질문 수)
- 모델 교체 시 회귀 테스트 대상. 골드셋은 실제 사용자 발화에 요소별 근거 구간을 주석해 만든다

### 6-3. 구글 드라이브 단독 저장 — 기각

검토했고 **주 저장소로는 기각**한다. 백업 어댑터로는 후보로 남긴다.

- **사용자에게 보이지 않는다.** `appDataFolder`는 숨은 공간이라 Drive UI에 나타나지 않는다 → *"내 데이터는 내 것"*이라는 소유감 효과가 **실제로는 생기지 않는다**
- **사용자의 저장 할당량을 소비한다.** 우리 비용이 0일 뿐, 사용자의 15GB를 쓴다
- **앱을 제거하면 데이터가 삭제될 수 있다.** 공유·이동·휴지통 불가
- **경쟁 10개 중 구글 드라이브 직접 저장 사례 0건.** 가장 가까운 것이 Plottr Classic의 Dropbox/iCloud **수동** 동기화

> 근거: `research-v3/A_오픈소스.md` §5.1~5.2 (Google 공식 문서 대조), `C_경쟁제품.md` §2.5
> 참고: `drivestash` 패키지의 "zero storage quota cost" 주장은 Google 공식 문서와 충돌한다. 검증 전 신뢰하지 않는다.

### 6-4. v2의 어댑터 주장 정정

v2 §6-2는 *"어댑터만 교체하면 화면 코드는 그대로"*라고 적었다. **코드상 성립하지 않는다.**

```ts
// engine/library.ts:38 — 동기 인터페이스
export interface WorkStore {
  list(): Work[];          // 배열을 즉시 반환
  save(work: Work): void;  // void
}
```

Dexie든 서버든 반드시 `Promise`다. 옮기는 순간 인터페이스가 async가 되고 **`/library`·`/studio`·`/create`에 로딩·에러·낙관적 업데이트 상태가 추가된다.** 이 비용을 0으로 적어둔 것이 v2의 오류다. §6-2 2번 단계의 실체가 이것이다.

### 6-5. 비용에 대한 사실

"DB를 클라우드에 올리면 비용이 많이 난다"는 걱정의 실제 원인은 저장소가 아니다.
Supabase 무료 티어(500MB + Auth)도, 구글 드라이브도 초기 비용은 0이다.

**실제 비용원은 `engine/models.ts`다** — `MODEL_MAIN`과 `MODEL_LIGHT`가 둘 다 `claude-opus-5`이고, 발화 추출까지 opus-5로 돈다.
이는 2026-08-26 "고객 만족 우선" 결정이며 **유지한다.** 내리는 기준은 `docs/model-policy.md`의 G1~G4가 전부 충족될 때뿐이고, 교체는 환경변수로만 한다.

**경쟁 공개 자료에서 확인되지 않은 것 — 우리 기회**

1. 자유 발화가 먼저이고 질문은 빈칸에만 최대 N개인 플로우
2. **발화 요소 추출 + 이미 말한 것 재질문 금지 계약** ← 가장 강한 후보(§2)
3. 로그라인의 관점 차이(정공법/관계/아이러니)를 비교 선택하는 단계
4. "후크는 AI가 채우지 않는다"는 명시적 보호
5. 초보자용 텍스트 구조화 → 웹툰 변환의 연속 흐름

> **표현 주의(P2)**: "아무도 안 한다"가 아니라 **"이번 10개 공개 표본에서 확인하지 못했다"**이다. 로그인 이후 화면은 확인하지 않았다.

## 14. 방향 갱신 (2026-09-01 사용자 결정)

### 14-1. UX 방향 — 재미와 속도

**신인 창작자가 질문에 답하는 것 자체에서 재미를 얻도록, 흐름을 빠르게 가져간다.**
기존 5단계 구조는 유지하되, 각 단계의 체감 속도·진행감·즉각 피드백을 끌어올린다.
구체 패턴은 리서치 D(UX 벤치마킹) 결과로 설계한다.

핵심 방식 (사용자 확인 2026-09-01 — 현재 구현과 일치, 강화 대상):
1. **질의응답을 통한 창작 지원** — 현행 2단계(빈칸만 질문)
2. **한 장면 → 나머지 채움** — "꿈을 꿨다", "장면이 떠올랐다"에서 시작. 현행 `/api/scene-blocks` 역산이 이 방식의 초기 구현

### 14-2. 비용 상한 — 하루 $20

`GUARD_DAILY=80` (최악 케이스 회당 $0.25 × 80 = $20). 근거: opus-5 $5/1M 입력 · $25/1M 출력.
설정 위치: `.env.local`. 운영 중 조정은 env로만.

### 14-3. 모델 — 지금은 opus(테스트), 장기는 자체 모델

- 현행 opus-5는 **품질 기준선 확보용(테스트)**이다. §6-5의 "고객 만족 우선" 결정과 양립한다.
