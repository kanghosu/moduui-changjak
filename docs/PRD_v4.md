## 1. 제품 정의 (갱신)

**Modu Story는 말하면 이야기가 되는 곳이다.** 사용자가 아이디어를 쏟아내면, 엔진이 김태원 「욕망의 레시피」 4막·24블록으로 구조를 세우고, 후크·감정·디테일은 사용자에게 남긴다. 신인 창작자가 **지도 완성까지 즐겁게** 가고, 완성 직후 **다음 한 장면**을 손에 쥐게 하는 것이 목표다.

- 타깃: 글로벌 신인 창작자(웹소설·시나리오·웹툰 지망). 1차 언어 영어, 2차 한국어·중국어.
- 단계: 대기리스트(현재) → 한국어 베타 → 3개 언어 정식.
- 정직 표기(v3 §4) 유지: "검증된 방법론" 금지, 무키 결과는 "규칙 기반 초안".

## 2. 원칙 (유지 + 1 추가)

v3 §3의 원칙 3(플롯은 AI·후크는 인간 / 방법론 IP 보호 / 구조 무결성)과 가설 5는 그대로.
**추가 원칙 4 — 즐거움은 결과의 즉시성에서 온다.** 뱃지·점수·퍼센트가 아니라, 내 말이 바로 카드·지도가 되는 것(리서치 E §2 최소 원칙). 흐름 문서 §3의 장치들이 이 원칙의 구현이다.

## 3. 흐름 (요약 — 정본은 `docs/흐름설계_v1_20260902.md`)

랜딩 → 쏟아내기 → 채우기(한 화면 한 질문, 없음·건너뛰기) → 방향 고르기(로그라인 3안 + 큰 포스터) → 지도 펼치기(24칸 착륙 + 완료 화면) → 다음 한 장면(15분) → 돌아오기(중단 지점).
대안 진입: 한 장면에서 시작(장면 역산). 측정 지표 6개는 흐름 문서 §6.

## 4. 다국어

- 경로: `/`(en 기본, Accept-Language ko/zh 자동감지 + 쿠키 우선) · `/ko` · `/zh`. 라이브러리 없이 `[lang]` 세그먼트 + JSON 사전.
- 앱 화면도 3개 언어(사용자 결정 "이번에 같이"). 엔진 출력 언어는 요청 `lang`을 프롬프트에 전달(캐시는 언어별 3벌).
- 무키 휴리스틱은 한국어 최적화 — en/zh에서는 표기.

## 5. Modu Design System v1 (방향 — 스펙은 별도 문서, 리서치 후 확정)

**가져올 것 (토스)**
- 측정 가능한 목표를 먼저 정하고 저비용 프로토타입으로 검증(toss.tech "업무용 툴, 내 동료가 정말 만족했나요?" — 만족도 2.71→3.88, 검색 10초→0초의 방식).
- 타이포 스케일을 **토큰으로 고정**(TDS는 `f11~f17…` 단계마다 fontSize·lineHeight(1.5)·icon·badge·link 패딩까지 세트로 정의 — 공개 CSS에서 관찰). 우리도 `t.f13 ~ t.f40` 세트 토큰.
- 한 화면 한 메시지, 큰 타이포, 제품 화면이 떠 있는 구성, 짧은 카피(toss.im/en-us).
- 접근성·모션 규칙을 시스템 안에(색 대비 AA, reduced-motion).

**우리 것으로 만드는 것**
- 두 층: **랜딩 = 극장(다크 #171717 + 테라코타 #F07A55)**, **서비스 = 작업실(종이 #F7F4EF + 테라코타 #B54E32)**. 섹션 전환으로 "극장에서 작업실로".
- 의미 색은 구조에만: 전환점·적대자·B스토리(디자인 시스템 §5-2).
- 서체 Pretendard(한·영), 중국어는 Noto Sans SC 폴백.
- 컴포넌트 최소 집합: Button·Input·Chip·Card·Sheet·Timeline24·ProfileCard·ProgressState(퍼센트 없음)·Toast.
- 문서 형식: 저장소 루트 `DESIGN.md`를 정본으로(오픈소스 DESIGN.md 사례 조사 후 구조 확정 — 리서치 R2).

## 6. 재구축 결정

**UI 층은 새로 만든다. 엔진·데이터·API는 유지한다.** 이유: 화면 12개가 구 스타일이고 사용자 평가가 "불충분"이며, 새 흐름(§3)과 디자인 시스템(§5)을 얹으려면 점진 수정보다 재구축이 빠르다. 반면 엔진(`engine/*`, `knowledge/method/*`, `benchmark-library.json`, 76편 AI 라이브러리, API 라우트 10개, 테스트 77개, G1~G15 수정)은 검증된 자산이라 버리지 않는다.

- 브랜치: `feat/v4-rebuild` (DM Maker-1 완료 후 `feat/p1-integration`에서 분기).
- 순서: 디자인 시스템 코드 → 랜딩 → 흐름 화면(쏟아내기·채우기·고르기·지도·작업실·서재) → 다국어 → 카피·접근성 검수.
- 기존 화면은 삭제 대신 `app/(legacy)/`로 옮겨 두고, 새 화면이 실브라우저 검수를 통과한 뒤 제거한다.

## 7. 개발 규칙 (사용자 지시 2026-09-02 — 모든 워커 브리프에 복사)

**R1 오픈소스 먼저.** 기능을 만들기 전에 같은 문제를 푼 오픈소스를 찾아 적용 가능한 것을 쓴다(라이선스 MIT/Apache/BSD만, 출처 주석 필수). 의존성 추가는 오케스트레이터 승인 후.
**R2 논문.** 사용자 행동·UX·서사 구조에 관한 결정은 논문 근거를 붙인다(리서치 B·E의 17편이 출발점). 근거 없는 결정은 "가설"로 표기.
**R3 리버스 엔지니어링.** 이미 있는 서비스(토스·Duolingo·Typeform·Sudowrite·Dramatica/Subtxt·Plottr 등)의 해당 화면을 먼저 분석하고 훔칠 것/피할 것을 적는다.
**R4 크롤링은 insane-search.** `tools/insane-search/skills/insane-search`의 `python -m engine <URL>`(공개 페이지 전용, 로그인·유료벽은 중단). 인용은 URL+조회일.
**R5 보고에 "선행 조사" 절 필수.** 무엇을 찾았고, 무엇을 가져왔고, 무엇을 못 찾았는지. 빈칸 허용, 지어내기 금지.
**R6 완료 기준은 test/tsc/build + 오케스트레이터 실브라우저.** 외부 린트 규칙 맞추기 리팩터링 금지.
